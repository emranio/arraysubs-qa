## Steps
1. On D2 resolve the registry hand-off and re-query it read-only. Require the user, `SUBID5`, parent order, `_gateway_payment_method_id`, `_next_payment_date`, `k5`, and both pending action IDs to match `SLT-CHK-05`. Publish the exact D3 charge row and `charge−5m` deadline to the registry and D02 watch report, leave this card `in-progress`, and set no renewal mail baseline yet.
2. On D3 no earlier than five minutes before the recorded `due+k5`, set `PRE5B=$(mailpit-agent latest-id)` in both handoff locations. After the gate passes, force nothing. `mailpit-agent wait-new "$PRE5B" 900 "Verify your subscription renewal"`; show/text the exact matching message, extract its action URL, and capture the message in the local Mailpit UI as `SLT-REN-05-01-verification-email.png` using `customer-SLT-REN-05`. Resolve the sole renewal order from the subscription's exact `_pending_renewal_order_id`, require a numeric ID plus the reverse `_subscription_id=SUBID5` and a +1 renewal-order count, then read its action-context meta, the exact AS rows, and logs; never select the order by recency.
3. Prove the renewal action log says `via WP Cron`; confirm the order is `wc-pending`, never `wc-failed`, and no retry action or payment-failed mail exists.
4. In `agent-browser --session customer-SLT-REN-05`, log in as `slt2-sca`, open the extracted URL, re-snapshot, and screenshot the HTTP-200 order-pay form. Require `wc-stripe-confirmation=1` plus the correct order key in the URL.
5. Immediately before completing the 3DS challenge and submitting payment, set `PAY_PRE=$(mailpit-agent latest-id)`. Submit once, run `mailpit-agent wait-new "$PAY_PRE" 300 "Payment received for subscription #$SUBID5"`, and reconcile every message newer than `PAY_PRE`. Capture the unpopulated pay form as `SLT-REN-05-02-pay-page.png` and the safe paid result as `-03-order-paid.png`; never capture evidence containing a full card number. Re-read the exact renewal order, subscription meta, newly armed exact AS rows, and logs.
6. Add the renewal order ID, verification Mailpit ID, action URL shape (redact the order key in prose), payment-success Mailpit ID, and post-payment schedule to the registry. Empty the cart if present and close only `customer-SLT-REN-05`.
7. Self-review this evidence, move `SLT-REN-05` through Review to Done, then cite the same renewal evidence in `SLT-CHK-05` and move that parent card through Review to Done. Never leave either card in Review.

## Expected results
1. The existing `SLT-CHK-05` checkout baseline remains one paid $10.00 parent order and one active subscription with a stored `_gateway_payment_method_id`; this task creates no second user, order, or subscription before renewal time.
2. At the D3 `due+k5`, `arraysubs_process_renewal` completes (`via WP Cron`) as a non-failure: the renewal order stays `wc-pending`, **never `wc-failed`**.
3. Order meta `_arraysubs_payment_action_intent_id`, `_arraysubs_payment_action_required_at`, `_arraysubs_payment_action_url` set, mirrored on the subscription; `_payment_retry_attempts` 0/absent, no retry queued, `_completed_payments` stays 1, status stays `arraysubs-active`.
4. The action URL is the order-pay URL plus `wc-stripe-confirmation=1` and the order key; as the logged-in customer it returns 200 with a pay form, not a 404 or My Account redirect.
5. Completing the challenge charges $10.00: order `wc-processing`/`wc-completed`, `_completed_payments`=2, `_pending_renewal_order_id` cleared, `_next_payment_date` advances to D4 at the original anniversary time (from `_renewal_scheduled_date`, so the delay adds no drift), fresh legs at `k5`.
